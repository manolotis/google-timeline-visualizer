## Import and data loading

<!-- CLAUDE.md, lines 56-58 at 293c757 -->
- **Data source** (`useData.ts`): an IndexedDB import, when one exists with the current `IMPORT_FORMAT_VERSION`, wins over `public/data/`; otherwise datasets are fetched from `/data/`. The choice (`loadDataSource`) and every dataset promise are cached at module level because pages unmount on nav (App.tsx conditionally renders the page named by the URL hash); failed loads are evicted so remounts retry. After an import is saved or cleared, `reloadData()` drops both caches and bumps a data version (a `useSyncExternalStore` store); hooks derive `loading` from a result whose version is stale instead of resetting state in an effect. Loaders passed to `useLoad` must be stable module-level functions (see `datasetLoaders`).
- **IndexedDB layout** (`src/import/storage.ts`): database `timeline-visualizer` v1; store `datasets` holds each dataset's **JSON text** keyed by `DatasetKey` (text, not objects, so reading one back is exactly like fetching its file and the import stays byte-comparable with the CLI); store `meta` holds the `ImportMeta` under `'import'` and the family-home config text under `'config'`. Saves and clears are single transactions. Don't open the database from test code without a version before the app has created it (that creates v1 with no stores).
- **The import worker** (`src/import/worker.ts`) is created per import by `importJob.ts` and terminated afterwards; the job state lives in that module (not a component) so it survives the drop zone unmounting. Vite only bundles it when created exactly as `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`, and `vite.config.ts` sets `worker.format: 'es'` because it lazy-loads `offline-city-db.json` and `airports.json` as separate chunks. It fetches the world geometry from `/world-countries.geo.json` (absolute, like useData). It reads the whole file into one string, so ~500 MB is the ceiling (V8's max string length; the worker refuses bigger files up front); an 83 MB export takes ~0.8 s and ~220 MB of extra renderer memory. Errors reach the UI as `{kind, message}` (`format`, `json`, `memory`, `read`, `other`, plus `crash`/`storage` from the main thread) — keep messages readable, they're shown verbatim.

## Nights and trips

<!-- CLAUDE.md, lines 55-55 at 293c757 -->
- A **night is keyed by the local date of the evening it begins**: night D is 20:00 on D → 08:00 on D+1, each candidate visit judged in its own local time (its start offset), and the visit overlapping that window most is where it was spent. If no visit overlaps but a flight (≤ 20 h; longer "flights" are gap-filler artifacts) is in the air at local midnight, the night counts at the flight's departure point, so an overnight flight home stays a night away. A night with no location at all defaults to home, **unless** the nearest located nights on both sides are away: then it carries the previous located night's place (forward only, so city resolution order is unchanged) — a mid-trip tracking gap (overnight bus, dead phone) must not split the trip, but a located home or family night still does. `nights-away.json` has one night per local date from the first segment's start to the last one's end. So a trip's travel days run from its first night's date to the day after its last night (`tripWindows` in `src/trip.ts`): outbound flights fall on the first night's date, return flights on the day after the last night or, for evening departures, on the last night itself. The calendar heatmap keys each cell by its calendar date string and shows the night with that key.

## Homes

<!-- CLAUDE.md, lines 63-65 at 293c757 -->
- **Home is a list of periods**: `home.json` is `HomePeriod[]` (`{start, end | null, lat, lng, city, country}`, oldest first, `end: null` = current home; see README "Home Periods"). Every night's `isHome`/`distKm`, and therefore trips and `geography.json` away nights, is measured against the home of that night's period. A night outside every period belongs to the nearest period in time, ties to the earlier one. That rule lives in **two places** that must agree: `periodIndexForDate` (`src/pipeline/homes.ts`) and `homePeriodsInRange` (`src/aggregate.ts`, which picks the Travel Map markers and the NightsAway header). `isStaleHome` catches the old single `{lat, lng}` file and the pages show a regenerate hint (`RegenerateHint`: import again or re-run preprocess).
- **Family homes** come from an optional config (`{ "familyHomes": [{lat, lng, label?, radiusKm?}] }`; see README "Family Homes"): for the CLI, `timeline-config.json` in the project root; in the browser, pasted or loaded in the import panel and stored in IndexedDB (`meta` → `'config'`) next to the import. Both validate with `parseTimelineConfig` (`src/pipeline/familyHomes.ts`), which throws on a malformed config (the CLI before the slow parse; the panel shows the message as you type and blocks the import). The file is **gitignored because it holds personal coordinates — never commit it, and never put real coordinates in `timeline-config.example.json`, README or code comments**; the example uses public landmarks. A night that would be away but lies within a family home's radius (nearest wins) gets `isHome: true` plus `family: <label>`, keeping `distKm` from the period home; home nights never get `family`, so a family home that is the period's home is plain home. Because family nights are `isHome`, every `!isHome` away count, trip grouping and `geography.json` away nights exclude them with no special casing; code that means "at your own home" (the home streak) must use `isOwnHomeNight` (`aggregate.ts`). The field is optional and only emitted on family nights, so without a config all pre-existing output files are byte-identical; `family-homes.json` (`FamilyHome[]`, `[]` without a config) is always written, and a missing one (older export) means no family homes, so `useFamilyHomes` failures are not errors. Travel Map family markers apply to a range only if a family night there falls in it (`familyHomesInRange`, matched by label).
- Home detection (`detectHomePeriods`) uses HOME/INFERRED_HOME visits only to nominate candidate places. The monthly evidence is **nights slept** within `HOME_RADIUS_KM` (1 km), because the labels are sparse (whole months unlabelled) and also get put on a family home during holiday stays. Don't switch it to counting labels. Candidates are clustered by distance, not the 0.1° city-DB grid: a home that sits on a bucket edge gets split in two by a grid. `HOME_MIN_PERIOD_MONTHS` (default 5; CLI env only) is the one tuning knob; merged segments count support *net* of the months that interrupted them, which keeps sparse 2013–14 data from forming a fake home. Home `city`/`country` come from `CityResolver.peek` (cache only, no lookups).

## Flights and airports

<!-- CLAUDE.md, lines 62-62 at 293c757 -->
- `scripts/data/airports.json` is **vendored, committed, and never fetched at preprocess, import or app runtime** — a trimmed copy of OurAirports' `airports.csv` (public domain), `large_airport`/`medium_airport` rows with an IATA code only, `{iata, name, lat, lng, municipality, size}`. Regenerate it with `npx tsx scripts/generate-airports.ts` (a one-off manual step with a network request, not part of `npm run preprocess`). The pipeline matches each flight endpoint to the nearest airport within 40 km (`findNearestAirport` in `src/pipeline/airports.ts`; a `large` airport gets a 5 km scoring discount over `medium` on near-ties) and estimates `co2Kg` per flight (`estimateFlightCo2Kg`: great-circle distance + 95 km detour, a DEFRA-style per-km factor by haul, × 1.9 RF multiplier — see the comment above that function, and README's [CO2 Estimate](../README.md#co2-estimate), for the exact factors and source).

## Travel Map

<!-- CLAUDE.md, lines 66-67 at 293c757 -->
- **Travel Map routes are one canvas layer**, not react-leaflet `<Polyline>`s: `RouteCanvasLayer` (`src/routeCanvas.ts`, a plain `L.Layer` positioned and zoom-animated like Leaflet's renderers) draws straight from `RouteIndex` (`src/routeIndex.ts`: routes sorted by event-local time, points pre-projected to zoom-0 world pixels in typed arrays). ~15k Leaflet paths were slow to mount and Leaflet's own canvas renderer repaints every path under a changed area, which rules out drawing one segment per frame. The base canvas only accumulates (playing forward draws just the new segments); a backward seek, a new selection or a pan/zoom end repaints it. Route style (opacity 0.4, widths) lives there now. The map uses `preferCanvas`, so markers are canvas-drawn too.
- **Playback position is not React state**: `PlaybackClock` (`src/playback.ts`) is an external store advanced by its own rAF loop, like route.ts but ephemeral (only `playback=on` is in the URL). The route layer redraws from `clock.subscribe`; components read it with `usePlaybackSelect`, whose selector must return a primitive so they re-render only when it changes (e.g. how many markers have appeared). Don't lift the time into `TravelMap` state — it would re-render the whole page (and 500 markers) every frame. Playback time is event-local wall-clock ms (`localTime`: the timestamp's local time read as UTC), so `playbackDate()` matches the dates the range filters by.
